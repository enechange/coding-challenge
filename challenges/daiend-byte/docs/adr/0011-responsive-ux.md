# ADR-0011: レスポンシブ・UX 方針（モバイルファースト）

## Status

Accepted

## Context

「スマホ表示をメインに考え、PCでは崩れなければ良い」という要件に沿ったレイアウト方針と、フォーム操作の体験を設計する。

## Decision

### PC表示時のレイアウト方針

- コンテンツに `max-w-md`（448px相当）を設定し画面中央寄せ。PC幅では左右に背景色の余白が広がる
- design.png のモバイルデザイン（1カラム縦積み）をそのまま保ち、間延びした見た目を防ぐ

### ブレークポイント設計

- ブレークポイントは設けない。全画面幅で同一の1カラムレイアウト（`max-w-md` 中央寄せ）とする
- フォームの構造上、画面幅でレイアウトを変える必然性がなく、「最小限で良い」という要件にも合致する

### エラー表示のレイアウトシフト対策

- 対象はカスケード欄（電力会社/プラン/契約容量）ではなく、既に後続フィールドが可視化されている場面でエラーが起きうるフィールド（電気代・メールアドレス）に限定される
    - カスケード欄は上流未解決の間そもそも下流フィールドが存在しない（[ADR-0005](./0005-form-validation.md)/[ADR-0006](./0006-api-abstraction.md) で確定した非表示設計）ため、「エラー表示による下流欄のシフト」自体が発生しない
- 電気代・メールアドレス欄は、領域を事前確保せず、エラー発生時に瞬間的に挿入する方式を採用
    - 実例検証: GitHub のサインアップフォーム（https://github.com/signup）のユーザー名フィールドで、無効な値を入力すると領域確保なし・アニメーションなしで即座にエラーメッセージが挿入され、下の「Your Country/Region」欄が瞬間的に押し下げられる挙動を確認。著名プロダクトでも許容されているパターン
    - 対象が最大2箇所（電気代→メール、メール→submitボタン）に限定されるため、常時領域確保による間延びよりもシンプルな実装を優先

### カスケードフィールドの出現UX

- 上流が確定し下流フィールドが新規に画面へ追加される際、出現アニメーション（`grid-template-rows` の 0fr→1fr 等）は入れるが、自動フォーカス移動は行わない
- 自動フォーカス移動はモバイルブラウザでのキーボード開閉・スクロール位置のジャンプ等、意図しない挙動のリスクがあるため見送り（a11y の観点は [ADR-0018](./0018-accessibility.md) で再確認済み）
- 検討の過程で ENECHANGE 自身の実サービス（https://enechange.jp/try/input）を調査し、「下流フィールドを常時表示し、前提未解決の間は無効化+案内文（『はじめに郵便番号を入力してください』）で表現する」という別パターンを確認したが、採用は見送り、[ADR-0005](./0005-form-validation.md)/[ADR-0006](./0006-api-abstraction.md) で確定した非表示方式を維持する結論とした
    - README「リアルタイムバリデーションを行い、invalidな場合は先に進めないようにする」は、フィールドの表示/非表示ではなく操作のブロックを指す要件であり、非表示方式でも要件を満たすと判断

### モバイルキーボード最適化

- 郵便番号・電気代の入力欄に `inputMode="numeric"` を指定する
- `type="number"` ではなく `type="text"` + `inputMode="numeric"` を採用（スピナーUIや `e`/`+`/`-` 入力の副作用を避けるための現在のベストプラクティス）
- この変更に伴い、[ADR-0005](./0005-form-validation.md) で決めた電気代フィールドの型変換方針を `z.coerce.number()` ベースに更新している

### submitボタンの活性/非活性の視覚的フィードバック

- 非活性時は薄いグレー背景（`#DDDDDD`）+ 濃い文字（`#444444`）とする。コントラスト比 約7.17:1（WCAG AAA基準を満たす）
- 検討過程での却下案:
    - 「背景opacity低下」案: ボタン全体（背景+白文字）に `opacity` を適用すると、背景・文字とも同じページ背景色に向かって透過し、フェード後の背景と文字のコントラストが約1.9:1まで低下し可読性を損なうことが判明したため不採用
    - 「濃い背景（`#444444`）+白文字」案: コントラスト比は良好（約9.74:1）だが、活性時の紺ボタンと視覚的な強さがほぼ同等になり、「非活性=控えめ」という一般的なUI慣習に反するため不採用
- トークン設計: 生の値を `gray`（`#DDDDDD`）として1箇所定義し、`border` と `disabled` の両方がこれを参照する（[ADR-0008](./0008-styling-tokens.md)）

## Consequences

- 正: レイアウト方針とブレークポイントが決まっており、モバイルファーストの要件を満たしつつPC表示も破綻しない
- 正: エラー・出し分け時のUX方針（レイアウトシフト対策含む）が実例検証に基づいて言語化されている
- 正: submitボタンの状態フィードバックがWCAG基準とUI慣習の両方を満たす
- 負: 自動フォーカス移動を見送ったことで、視覚障害のないユーザーにとっては次フィールドへの遷移が手動になる（トレードオフとして許容）
