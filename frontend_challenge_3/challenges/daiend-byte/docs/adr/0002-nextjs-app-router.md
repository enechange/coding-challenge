# ADR-0002: レンダリング戦略に Next.js（App Router）を採用する

## Status

Accepted

## Context

[ADR-0001](./0001-react-selection.md) で React を採用した。React エコシステム内でも Vite（純SPA/CSR）を使うか Next.js（SSR/SSG メタフレームワーク）を使うかは別の決定事項であり、[ADR-0003](./0003-directory-structure.md)（ディレクトリ構成）・[ADR-0007](./0007-toolchain.md)（ツールチェーン）・[ADR-0015](./0015-cicd-deploy.md)（CI/デプロイ）の前提になるため先に確定する。

README の記載「github-pages 等で...閲覧できる環境を作成してくださるのが好ましい」は、デモを閲覧するための手段についてのソフトな推奨であり、本番のデプロイ先を規定するものではない。したがって本判断は、提出物の閲覧手段（デモホスティング）と本番プロダクトのアーキテクチャを分けて考え、後者を基準に行う。

判断基準:

- 今回の提出物（フォーム1画面）だけでなく、事業ドメインの成長軌道を踏まえた妥当性
- フレームワーク移行コスト（後から SSR/SSG が必要になった場合の作り直しコスト）
- 今回の提出物における複雑さの増分とのバランス

検討事項:

- ENECHANGE のような比較・シミュレーションサービスは、SEO 経由の自然検索流入が事業の生命線になりやすいドメイン（地域別・電力会社別のロングテール検索等）。これは「あるかもしれない将来機能」ではなく、この事業モデルではほぼ確実に必要になる要件であり、SSR/SSG の恩恵を強く受ける
- CSR の SPA を後から SSR/SSG 対応に移行するのは、ルーティング・データ取得方式・ホスティングを含めた作り直しに近く、業界的によく知られた高コストな移行（CRA→Next.js 移行と同型の問題）。先に正しいフレームワークを選ぶ方が長期的に安い
- 今回の提出物自体は SSR を直接使わないフォーム1画面だが、それは「今回作る機能が少ない」だけであり、フレームワーク選定は目先の実装物ではなく事業の成長軌道に対して行うべき
- 提出用デモの閲覧先（GitHub Pages 等）は本番アーキテクチャと切り離して考えてよく、デモの都合でフレームワーク選定を歪めるべきではない

## Decision

Next.js（App Router）を採用する。本番は SSR/SSG 前提の Node/Edge 対応ホスティングを想定する。

波及する決定:

- **CI/デプロイ（[ADR-0015](./0015-cicd-deploy.md)）**: 提出デモは GitHub Pages への static export ではなく、Next.js をそのままホストできる Vercel 等を使う。選定したアーキテクチャ通りに動くデモにするため
- **ディレクトリ構成（[ADR-0003](./0003-directory-structure.md)）**: `app/` はルーティングの薄い殻として使い、ドメインロジック・コンポーネントは bulletproof-react 流の `features/` 配下に置く（`app/` が `features/` を呼び出す構成）。bulletproof-react は Vite/CRA 前提の構成例だが、この原則は Next.js の `app/` とも共存可能
- **ツールチェーン（[ADR-0007](./0007-toolchain.md)）**: ビルドツールは Next.js 標準のツールチェーンに従う
- **[ADR-0001](./0001-react-selection.md) との整合**: 「React ならメタフレームワークへの拡張性を将来に残せる」とした選択肢を、今回すぐに行使する一貫した判断

## Consequences

- 正: SEO・コンテンツ成長・多ページ化に対して作り直しなしで対応できる
- 正: 選定したアーキテクチャ通りに動くデモを提示でき、レビュー時の説明に一貫性がある
- 負: フォーム1画面のみの今回の提出物に対しては、Next.js の学習・セットアップの複雑さがオーバースペックに見える可能性がある。この判断根拠を ADR に明記することで説明可能にしている
